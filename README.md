# Completion certificates for course cohorts

From a platform standpoint we start by auditing the educator's decision boundary: if the completion timestamp lands on or before the learner deadline we emit a certificate, otherwise a late or missing timestamp yields a report with no PDF, and that branching drives our SLO for certificate generation latency.

The sample we ship is a small TypeScript module with an executable, but in production I'd wrap the call in a Go http client with a context timeout because our error budget can't absorb unbounded hangs. It fires one explicit HTTP`POST`to Infrai's`pdf.generate`endpoint. Infrai gives us one key and one bill across every capability, so the same`INFRAI_API_KEY`token covers this workflow without spinning up separate credential management.

## Run the business check

```sh
npm install
npm test
```

That test is deliberately narrow: it feeds an on-time, a late, and a missing completion, then asserts`completed-on-time`,`late`, and`incomplete`decisions so we have a minimal SLO guardrail before this goes on-call. We don't simulate load here because the certificate volume per cohort is low, but capacity planning still says keep the retry budget separate.

## Generate a real PDF

Export`INFRAI_API_KEY`, then run the sample:

```sh
INFRAI_API_KEY=your_key npm start
```

Our client constructs certificate HTML from a domain record and ships`page_size`,`orientation`, and`store`alongside it; before we trust the HTTP status we decode the`{ok, data, error, metadata}`envelope, hand back the generated bytes, and apply exponential backoff on 429 because our SLO for user-facing PDF generation assumes bounded retry cost. If the envelope is rejected we surface an`InfraiError`that carries the upstream code and status so the HTTP handler can map it cleanly to the caller without leaking internals.

## Shape to extend

`Completion` defines the contract for course delivery reporting, capturing learner identity, course title, completion time, and deadline, and we treat that as the capacity unit for our storage planning. Persist that record in your queue or database, call`decideCertificate`before the write, and store the returned PDF bytes next to the learner id so you avoid a read-modify-write race. The executable stays tiny on purpose, keeping the request boundary auditable instead of hidden behind a framework.

The snippet above is copy-paste simple, which is fine for a prototype but we still need to weigh the managed call against self-hosting the PDF render farm, and the on-call load of maintaining chromium nodes loses on every review.
